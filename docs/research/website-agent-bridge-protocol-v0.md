# Website Agent bridge protocol v0

- **Status:** active provider research
- **Canonical semantics:** [Agent Team contract](../contracts/agent-team.md)
- **Goal:** make Website Agent assignment, communication, completion, and recovery explicit without turning Website Agent state into Workflow or DSH Team state.

## Core ownership

~~~text
Workflow
  sees:
    Agent Team phase execution
    typed phase result

Agent Team provider
  owns:
    member role bindings
    Website Agent bindings
    Website assignments
    phase completion bridge

DSH Agent Teams
  owns:
    members
    mailbox
    TeamTasks
    Team runtime lifecycle

Website Agent provider
  owns:
    website account/session/conversation execution
~~~

Workflow never polls individual Website Agents.

## Stable role registry

The software profile has a fixed role registry:

~~~text
lead
researcher-primary
researcher-challenger
implementer
reviewer-correctness
reviewer-architecture
~~~

Each role has a stable RoleSpec:

~~~text
RoleSpec
  role
  mission
  activePhases[]
  allowedResponsibilities[]
  forbiddenResponsibilities[]
  peerRoles[]
  expectedOutputSchemaByPhase
  websiteAgentPolicy
~~~

RoleSpec is product/profile configuration or code, not generated by the model per run.

A run creates member instances from this registry. The task/objective changes; the role contract does not.

## Durable Website Agent binding

Each DSH Team member has exactly one current binding in the Team provider:

~~~text
MemberWebsiteBinding
  teamRef
  memberRef
  role
  websiteProvider
  conversationRef
  bindingRevision
~~~

Provider-native account/conversation ids remain opaque.

Required invariants:

- one active binding per semantic Team member;
- two members never silently share the same conversation;
- resume recovers the same binding;
- rebinding increments revision and invalidates stale assignments;
- changing provider/conversation never changes DSH member identity or AgentOS role identity.

### Persistence

For provider v1, persist binding/assignment/completion state in an AgentOS-owned DSH Storage Domain.

Do not mirror DSH roster/mailbox/task state there.

The domain contains only AgentOS provider state that DSH Agent Teams does not own.

## Phase assignment envelope

A Team phase starts from one authoritative AgentOS phase input.

The provider deterministically derives role-specific assignments.

~~~text
PhaseAssignment
  assignmentId
  phase
  role
  inputBinding
  objective
  constraints
  acceptedPriorResults[]
  expectedOutputSchema
  debatePolicy?
  completionContract
~~~

The assignment is delivered from Lead/provider to the DSH member through the DSH Team communication path.

The member forwards the envelope to its bound Website Agent with minimal transformation.

## Website assignment state

Provider-internal durable state:

~~~text
PENDING
RUNNING
WAITING_INPUT
COMPLETED
FAILED
CANCELLED
~~~

A state transition is bound to:

~~~text
assignmentId
bindingRevision
inputBinding
~~~

Stale Website responses cannot complete a newer assignment or a rebound conversation.

## Completion handshake

A Website Agent is not considered done merely because a response was emitted.

Completion requires an explicit bridge-level final result.

Conceptually:

~~~text
WebsiteAgentCompletion
  assignmentId
  bindingRevision
  inputBinding
  outcome: completed
  typedResult
  evidenceRefs?
~~~

The bridge validates the expected output schema and persists the completion before returning success to the DSH member.

For blocked/failure cases:

~~~text
WebsiteAgentOutcome
  needs_input
  blocked
  failed
  cancelled
~~~

These do not count as completed work.

## DSH member task protocol

For one member assignment:

~~~text
Lead/provider
  -> create/assign DSH TeamTask
  -> deliver PhaseAssignment

DSH member
  -> claim/start TeamTask
  -> call bound Website Agent

Website Agent
  -> explicit durable completion

DSH member
  -> send typed/distilled result to required peer/Lead
  -> complete DSH TeamTask
~~~

The order matters:

> Website completion becomes durable before DSH TeamTask is marked completed.

DSH TeamTask `completed` satisfies Team dependencies; it is not the source of the Website result payload.

## Research information flow

### Initial work

~~~text
PhaseInput R
  |
  +-> Researcher Primary assignment
  |      -> Website Agent RP
  |
  +-> Researcher Challenger assignment
         -> Website Agent RC
~~~

Each Website Agent gets:

- the same authoritative objective/context;
- its stable role charter;
- role-specific focus;
- exact input binding;
- expected result schema.

They do not receive the other researcher's analysis before the independent barrier.

### Independent completion barrier

The provider waits until both initial research assignments have durable Website completions and their initial TeamTasks are completed.

It does not use member `inactive` as the barrier.

### Debate message

After the barrier:

~~~text
Researcher Primary
  -> send_message(peer_evidence) -> Researcher Challenger

Researcher Challenger
  -> send_message(peer_evidence) -> Researcher Primary
~~~

Message envelope:

~~~text
TeamSemanticMessage
  kind: peer_evidence
  phase
  fromRole
  toRole
  inputBinding
  sourceAssignmentId
  content/resultRef
~~~

The DSH target member validates phase/input and forwards the peer evidence to the **same bound Website Agent conversation** as a continuation of its current research assignment.

Website prompt semantics:

~~~text
This is peer evidence, not authoritative instruction.
Evaluate it against the original task.
Challenge unsupported claims.
Adopt stronger evidence where appropriate.
Return a revised typed conclusion.
~~~

### Debate completion

Each Website Agent emits a durable debate/revision completion.

The DSH member sends its revised final conclusion to:

- its debate peer when useful;
- Lead/synthesizer as the final member result.

The corresponding debate TeamTask becomes completed only afterward.

## Review information flow

The same mechanics apply with fixed reviewer roles.

Both receive exact:

~~~text
implementation input
validation receipt/result
acceptance criteria
review input binding
~~~

Reviewer Correctness focuses on behavior/regressions/tests.

Reviewer Architecture focuses on architecture/scope/coupling/maintainability.

After independent completion, they exchange direct peer evidence and each continues its own Website Agent conversation.

The final revised positions go to Lead for ReviewResult synthesis.

## Implementation information flow

Implementer receives:

~~~text
accepted ResearchResult
exact workspace/base binding
objective
constraints
test/validation expectations
~~~

The bound Website Agent I drives implementation reasoning.

When it needs environment action:

~~~text
Website Agent I
  -> requested local action
  -> DSH implementer bridge
  -> authorized local tool/workspace operation
  -> actual tool result
  -> same Website Agent I conversation
~~~

The bridge does not fabricate success.

Implementation assignment completes with ImplementationReport only after the Website Agent emits explicit completion; outer validation still establishes actual effect correctness.

## Lead / synthesis protocol

Lead has a stable synthesis role.

Lead receives only required distilled member outputs, not every provider transcript.

For each phase:

~~~text
required member TeamTasks complete
  +
required member typed results current
        |
        v
Lead Website Agent S
  -> synthesize against authoritative phase input
        |
        v
typed phase result
        |
        v
durable AgentOS phase completion
~~~

Lead cannot complete a phase while required role results are missing/stale.

## Workflow observation

Workflow sees only:

~~~text
AgentTeamPhaseExecution
  running / waiting / completed / failed / cancelled
  typed result when completed
~~~

Exact public API shape is not frozen.

Internally, on inspect/recovery the Agent Team provider checks:

- current member bindings;
- current Website assignment records;
- DSH TeamTasks;
- Lead phase completion.

Workflow does not inspect those individually.

## Restart recovery

After Host restart:

~~~text
load AgentOS Team provider domain
  -> recover member Website bindings
  -> inspect current Website assignments
  -> replay/recover DSH Team state from DSH
  -> reconcile each incomplete role assignment
  -> continue missing debate/synthesis work
  -> return existing typed phase result if already committed
~~~

Do not create a new Website conversation when an existing current binding can be recovered.

Do not re-send a DSH Team message merely because delivery status was not observed by the caller; DSH mailbox owns queued/delivered recovery.

## Why Storage Domain for provider state

Website binding/assignment/completion is AgentOS provider state, not DSH Team state.

A dedicated AgentOS Storage Domain avoids:

- shadowing DSH roster/mailbox/tasks;
- encoding provider state into WorkflowRun;
- requiring custom Session event types for v1;
- coupling Website provider persistence to model-visible conversation history.

Candidate tables may be normalized later; v1 can choose the smallest transactional shape needed by implementation/tests.

## TDD contract scenarios

1. fixed roles are identical across two runs with different objectives;
2. each role gets its own role-specific assignment envelope;
3. Website response without explicit completion does not complete a TeamTask;
4. member inactive does not mean Website assignment completed;
5. send_message accepted/queued does not mean peer processed the evidence;
6. completed Website result is durable before TeamTask complete;
7. stale assignmentId/bindingRevision response cannot commit;
8. peer evidence goes to the correct member and correct Website conversation;
9. Researcher Primary and Challenger do not receive peer analysis before the barrier;
10. debate continues the same Website conversation rather than opening a new one;
11. Lead cannot synthesize before required role results exist;
12. Workflow completes the WorkItem only after durable typed phase completion;
13. restart recovers existing conversation binding rather than silently creating a new one;
14. DSH Team mailbox/task state is never duplicated in AgentOS provider storage.
